# Interface system

HandoffGlass uses one visual vocabulary across its first-run setup, human decision panel, scene overlay and product site. The interface is intentionally small: the user should see **the next action**, not a dashboard of agent internals.

## Surfaces

| Surface | Purpose | Implementation |
|---|---|---|
| Desktop setup | Connect a host, inspect the exact MCP configuration, choose preferences | `src/desktop/setup.html`, `setup.css`, `setup.js`, `setup.mjs` |
| Human handoff | Display the current task and receive an explicit response | `src/desktop/panel.*` |
| Screen overlay | Point to an observed target without intercepting mouse input | `src/desktop/overlay-renderer.mjs`, `overlay.css` |
| Product site | Explain and preview the workflow | `site/` and `assets/` |

## Palette and themes

Shared desktop colors are defined in `src/desktop/ui-tokens.css`. Default: follow the OS; explicit `dark` and `light` override this when saved by the user. Every piece of status text uses the same token pair rather than a color-only distinction.

- Background: cool graphite (`#09131a` in dark mode), soft mineral white (`#edf2ef` in light mode).
- Accent: mint; used for primary action and grounded target highlights, not generic section decoration.
- Text: system-rendered fonts; no remotely loaded fonts, no rasterized text in live UI.
- Surfaces: thin borders, one soft shadow, no stacked opaque gradients behind body copy.
- Art direction: geometric frames, precise paths, a small amount of glow around the actual next step.

Vector illustrations include accessible SVG titles and descriptions. The three-language README illustrations remain scalable at any display density. Icons are produced from deterministic local source files; large exported PNGs are optional distribution assets, not dependencies.

## Motion

- Human decisions must remain immediately readable; progressive entrance is decorative only.
- Handwritten paths animate once when they appear; they do not keep redrawing.
- Steady-state pulse is subtle and can be turned off.
- `prefers-reduced-motion` overrides expressive animations; `forced-colors` replaces glow-dependent distinctions with clear outlines.
- Hover transitions do not gate keyboard or touch navigation.

## Copy and information hierarchy

**Title → action context → decision → confirmation of receipt.** A human-reported completion is not task verification. The panel never claims the target app accepted a decision before the broker reports the outcome.

Keep paragraphs under three sentences in normal operation. Present the long JSON configuration inside a scrollable, keyboard-focusable code area, not in the introductory text. The host selector changes the code preview; copying is a separate, user-initiated action.

## Design and API invariants

- Renderer IPC is limited to a local window and a small allowlist.
- No remote scripts, fonts, telemetry, screenshots, or remote image requests.
- The MCP configuration preview is generated by the same `hostConfig()` function used for clipboard export and CLI configuration. Previewing does **not** write another application's settings.
- Both packaged and Electron source-mode configuration use `ELECTRON_RUN_AS_NODE=1`; an Electron executable must not be launched in graphical mode by a stdio MCP host.
- Appearance settings are user-owned; agents cannot overwrite saved preferences through tool arguments.
- Theme `system | dark | light` is backward compatible with old preferences files lacking `theme`.
- Source and desktop application are not assumed to be installed on a remote/cloud agent's machine.

## Validation

```sh
npm run verify
npm run test:integration
npm run gallery
npm run desktop:demo     # macOS/Windows interactive graphical session
```

CI validates deterministic rendering contracts and packaged MCP entry behavior. A GUI-on-a-real-computer acceptance pass still covers font rendering, focus, passthrough, high-DPI monitor layout, system permission windows and accessibility contrast.
